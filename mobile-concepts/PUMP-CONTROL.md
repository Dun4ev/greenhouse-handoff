# Управление насосами теплицы

## Что предусмотрено в шкафах

В каждой зоне свой силовой шкаф ЩС, свой шкаф автоматики ША-У и два насоса. Н1 перекачивает раствор из выбранной емкости Е1, Е2 или Е3 в Е4. Н2 подает раствор из Е4 на участки полива. У зоны 1 три участка К4-К6, у зоны 2 шесть участков К4-К9. Обозначения насосов и каналов повторяются в каждой зоне, поэтому для команды нужны площадка, зона и насос. В сербской документации те же насосы обозначены N1 и N2. Выпуск v01 от 19.10.2026 имеет статус проекта для согласования. [Русский оригинал, разделы 1-3](../документы/greenhouse_consolidated_ru_v01.docx) · [Сербская версия, разделы 1-3](../документы/greenhouse_consolidated_sr_latn_v01.docx)

| Сигнал в каждой зоне | Направление | Что означает |
| --- | --- | --- |
| A1.DO1 / A1.DO2 | ША → ЩС | Запрос работы Н1 / Н2 соответственно. ША удерживает сухой контакт замкнутым, размыкание снимает запрос. |
| A1.DI1 / A1.DI3 | ЩС → ША | Включен контактор Н1 / Н2. Вращение двигателя этими сигналами не измеряется. |
| A1.DI2 / A1.DI4 | ЩС → ША | Разрешение по исправности Н1 / Н2. Ноль или обрыв блокирует пуск. Наличие контактов предстоит проверить. |
| A1.DI5 | ЩС → ША | ЩС разрешает дистанционное управление. |
| A1.DI6 | ЩС → ША | FS1 после Н2. Дискретный признак наличия потока. Расход, объем и поток Н1 по нему определить нельзя. |
| A2.DI1 / A2.DI4 | Внутри ША | SA1 в режиме АВТО / реле разрешения K0 взведено. Местная кнопка SB0 взводит K0. |
| A2.DI2 / A2.DI3 | Внутри ША | Новый фронт SB1 запрашивает пуск цикла. SB2 сбрасывает аварию. Для следующего пуска нужен новый запрос. |

Назначения каналов приведены в таблицах раздела 3 сводного документа и в спецификации. Обратная связь по положению поливных клапанов в базовом составе отсутствует. A2.DI5 и A2.DI6 зарезервированы под уровни Е4. HM-100 показывает pH, EC и температуру на месте, передача этих измерений в Pi не подтверждена. [Спецификация шкафа ред. 05, лист «Выходы», строки 5-20, и лист «Входы», строки 5-16](../документы/Спецификация_одного_шкафа_ред05.xlsx)

## Пуск, останов и расписание

- **Н2, полив.** Будущая локальная программа сначала запрашивает открытие клапана выбранного участка, затем запрашивает Н2. Участки поливаются последовательно. Перед сменой участка программа снимает запрос Н2. Потеря потока должна снимать запрос Н2 и фиксировать аварию до ручного сброса. Выдержки на клапаны и FS1 предстоит подтвердить при наладке.
- **Н1, подача в Е4.** Для рабочего режима предстоит подтвердить пригодность насоса PARKSIDE для раствора и поведение приводов К1-К3. Автоматическую подачу удобрений до решения этих вопросов проект не разрешает.
- **Останов.** Квитанция о принятии запроса, снятие запроса работы и отключение контактора дают оператору три разных сведения. При устаревших данных или потере связи фактическое положение контактора и поток неизвестны. Экранная команда останова служит для штатного управления. Аварийный останов с подтвержденным PL/SIL в документации не заявлен.
- **Расписание.** Проект предусматривает настройку длительности полива каждого участка при наладке и локальные часы RTC. Время суток для пуска, дни повтора и обработка пропущенного запуска подлежат согласованию. Редактируемое в демо время начала относится к новому интерфейсу.

При потере локальной связи между Pi и модулями проект требует снять команды. Восстановление связи или питания само по себе не должно запускать цикл. Поведение при теплом перезапуске МК с сохраненным питанием 24 В остается открытым вопросом. Влияние потери *облачной* связи на автономную работу предстоит проверить отдельно. ## Как подключается экран в демо

Карточка зоны управляет поливом через Н2. Демо предлагает задать ежедневное время начала по часам модели. Время сохраняется в локальном хранилище этого браузера, отдельно для каждой площадки и зоны. Модель отрабатывает расписание, пока активна подписка на ее обновления. В демо на участок отведено 60 секунд, между участками Н2 отключается на один такт модели. Полевые уставки определяются при наладке. [Модель пуска, останова и расписания](src/data/adapters/mockPumpControl.js)

Экран читает `zone.control` из снимка. Блок содержит время `scheduleTime`, фазу цикла `phase` (включая переход `switching`), доступность действий `canStart`, `canStop`, `canSchedule`, состояние контактора `contactor` (`on/off/unknown`), блокировки `fault` (`clear/active/unknown`) и разрешения `permit` (`granted/blocked/unknown`). Значение `null` означает, что источник не предоставляет этот блок. Состояние FS1, свежесть телеметрии и связь приходят отдельно. Для реального источника нужно согласовать, как формируются `fault` и `permit` из входов шкафа и логики контроллера. По одному разомкнутому контакту «исправен» причину блокировки установить нельзя. [Нормализация сигналов и доступных действий](src/data/pumpControl.js)

Через `provider.commandZone({ siteId, scenarioId, zoneId, action, time })` экран запрашивает пуск (`start`), останов (`stop`) или изменение расписания (`schedule`). Для расписания `time` имеет вид `HH:MM`, значение `null` отменяет запуск по времени. При успешном выполнении адаптер возвращает новый снимок. Это внутренний интерфейс браузерного приложения. Формат обмена с сервером будет определен отдельно.

### Как проверить локально

Из корня проекта запустите `python3 -m http.server 4187 --bind 127.0.0.1 --directory mobile-concepts` и откройте [мобильное приложение](http://127.0.0.1:4187/hybrid.html?site=srb-pilot-1&scenario=normal). В русской версии откройте «Насосы», в сербской - «Pumpe». Язык меняется в настройках.

Для проверки пуска по времени откройте штатный сценарий по ссылке выше. В свободной зоне задайте ближайшую следующую минуту **по часам модели**, сохраните и оставьте Live включенным. При наступлении этой минуты проверьте участок, контактор, FS1 и запись в ленте. После ручного останова проверьте состояние зоны и сохраненное время следующего пуска. Слой данных проверяется командой `node --test mobile-concepts/tests/pump-control.test.mjs` в Node.js 22 или новее.

## Что согласовать для тестового API

1. Уточнить у Андрея Наумова название и адрес стенда, версию и примеры обмена. Обозначение «DAST API» из обсуждения в доступной проектной документации не определено.
2. Зафиксировать, что именно запускает оператор для Н2 (участок или цикл) и для Н1 (источник и условие завершения перекачки). Определить приоритет местного управления, ручного останова и расписания. Проверка разрешений и блокировок нужна на стороне исполнения.
3. Согласовать идентификаторы площадки, зоны, насоса и запроса, права пользователя и ответ на повтор запроса. Предусмотреть отказ с причиной и неопределенный результат при разрыве связи после отправки. Принятие команды и новую телеметрию связывать по идентификаторам и времени источника.
4. Определить часовой пояс площадки, правила перехода на летнее время, пересечения запусков и пропущенного времени. Установить, где хранится утвержденное расписание, кто его исполняет и как обнаружить конфликт двух правок. Работа расписания на объекте должна быть независима от того, открыта ли вкладка.

## Развертывание позднее

Статические HTML, CSS и ES-модули фронтенда можно отдавать из отдельного веб-контейнера. При подготовке образа включать только файлы приложения. Адрес и версию API задавать в точке выбора адаптера. Бэкенд Наумова и исполнительную логику контроллера можно выпускать независимо. Приемку начать со стенда с синтетическими сигналами, включая повтор команды, отказ, потерю связи и устаревший снимок.
